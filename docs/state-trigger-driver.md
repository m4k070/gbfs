# ステートトリガ型入力ドライバ — $CFA7 はフレーム時計にならない (2026-10-10 実測)

道具: `tools/state_trigger_driver.fsx`（fsi スクリプト）。
ROM: Pocket Monsters Crystal (Japan) / マシン: `Memory.Cgb` / 入力系列: `scratch/pyboy_game_seq.txt`
（`7535 start → 7750 a → 以降 a を 120 フレーム間隔で 423 回`）/ hold = 3 フレーム。

## 結論

1. **`$CFA7` は「ゲームがフレーム待ちループに入っている」ことの観測点**としては正しい。
   ゲームが待ちループに入っている区間では、**LY wrap と 1:1** で 1 フレーム 1 回立ち下がる
   （ウォーム 60〜2400 フレーム後の 20 万ステップ窓で lyWraps=16..20 に対し cfa7Falls=15..20）。
2. ただし **フレーム番号の代用にはならない**。名前入力・性別選択・メニューなど、
   VBlank ハンドラ `$02FD` が動かない局面では `$CFA7` は**まったく落ちない**。
   そこを待つスケジューラは永久に停止する。
3. したがって計画の前提「押下はフレーム数ではなくメモリフラグの変化でトリガする」は、
   `$CFA7` については**実測で否定**された。

## A/B (16,000 フレーム上限、同じ入力系列・同じ hold)

| mode | 押下回数 | flagFalls | flagFalls/frame | 到達した局面 (16,000 フレーム時点) |
|---|---|---|---|---|
| `frame`（フレーム数駆動） | 59 | 12,414 | 0.776 | **本編（プレイヤーの部屋）** frame 14,650 |
| `flag`（`$CFA7` 駆動） | 4 | 9,448 | 0.591 | 性別選択画面（「おとこ / おんな」）で停止 |
| `settle`（画面が30フレーム静止したら押す） | 16 | 15,880 | 0.993 | タイトル画面のまま |

- `flag` モードは 4 回押した後、次の目標（flagFalls=9,370 の次 = 9,490）に届かず、
  16,000 フレームの上限まで進んで終わった。ゲームは性別選択で入力を待っており、
  `$CFA7` が落ちないため押下が発火しない（デッドロック）。
- `settle` モードは「静止したら押す」なので起動ロゴ（frame 45/115/220/322）で押し、
  以降は画面が常に動いているためほとんど押せない。16 回でタイトル止まり。

## 押下時刻の比較（同じ入力 i が何フレーム目で撃たれるか）

| i | target (PyBoy タイムライン) | `frame` モード | `flag` モード |
|---|---|---|---|
| 0 | 7,535 | 7,535 | 7,697 (falls 7,535) |
| 1 | 7,750 | 7,750 | 7,921 (falls 7,750) |
| 2 | 9,250 | 9,250 | 9,438 (falls 9,250) |
| 3 | 9,370 | 9,370 | 9,559 (falls 9,370) |
| 4 | 9,490 | 9,490 | 発火せず |

`flag` モードは「ゲームのフレーム解放 N 回」を時計にするので、同じ入力が
emulator フレームでは 150〜190 フレーム遅れて撃たれる。ずれは一定ではなく、
ゲームが待ちループに入っている割合（`flagFalls/frame`）に依存して伸びる。

## PyBoy との突き合わせ（同じ系列・同じ hold=3）

- gbfs `frame` モード: VRAM bank0 のハッシュが **frame 14,650 の押下 (#47) で
  `b92146a502f2e02e` に一致**し、以降 16,000 まで不変（画面はプレイヤーの部屋。
  4 階調 PNG を目視で確認）。
- PyBoy 2.8.1（`window="null"`）: 同じ系列で **frame 14,650 に同じハッシュ
  `b92146a502f2e02e`**、frame 14,700 の画面もプレイヤーの部屋。
- つまり **この harness では gbfs と PyBoy は同じフレームで本編に入る**。
  wiki にある「PyBoy は約 59,972 フレーム」は**再現しなかった**（hold の与え方が
  違う harness だった可能性が高い。未検証）。「入力タイミングの増幅 4 倍」は
  この測定条件では存在しない。

## 使い方

```bash
nix develop -c dotnet fsi tools/state_trigger_driver.fsx -- <rom.gbc> <seq.txt> \
    --mode frame|flag|settle --frames 16000 --hold 3 --log-every 200 \
    --out out.csv --png out.png --ascii out.txt
```

CSV は `press,...`（押下時刻）と `state,...`（200 フレームごとの画面/VRAM ハッシュ）の 2 種。

## 実装上の注意

- `hold` は**フレーム数**で数える。`flag` / `settle` モードは 1 ループで複数フレーム進むので、
  ループ回数で数えるとボタンが数百フレーム押しっぱなしになる（実測で `flagFalls/frame` が
  0.59 → 0.99 に化けた）。解放は `advanceFrame` のフレーム境界で行う。
- `$CFA7` は WRAM 固定バンク `0xC000-0xCFFF` の `0xFA7`。`Memory.read 0xCFA7` と一致することを
  起動時に検査している。
- フレーム境界は `Emulator.runFrame` と同じ判定（`oldLY > 0 && LY = 0`）を自前で回している。
  1 フレーム ≈ 9,400〜12,100 ステップ（Crystal JP 実測）。
